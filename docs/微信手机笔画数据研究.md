# 微信手机笔画数据研究

核查日期：2026-10-14。研究对象是微信输入法 **Android 手机端 4.0.0**，不是 Windows 微信输入法。仅静态读取 APK 和数据文件，未安装、启动或执行手机引擎，未操作手机或 Windows 输入框。

## 来源与可重复验证

- 官方下载入口：<https://z.weixin.qq.com/android/download?channel=website>
- 本次入口重定向：<https://download.z.weixin.qq.com/app/android/4.0.0/wxkb_1382_32.apk>
- 安装包长度：227,669,360 字节。
- SHA-256：`940586c40ca1ddb7d7190a727c9a3e2846c5a30b290de427da8c24df814b9603`。
- 数据来源：APK 内 `assets/config/beta/rsd.bin` 和 `assets/config/beta/sd.bin`。
- 资源索引版本：`rsd.bin` 为 958，`sd.bin` 为 1542；解析时核对 `index.json` 中的 MD5，并另记 SHA-256。
- 自编解析程序：`scripts/Extract-Wetype-Mobile.py`。固定校验上述安装包哈希，未知版本拒绝解析。
- 本地研究输出：`.verification/wetype-mobile/reproducible-export/`。此目录被 Git 忽略，尚未接入或随 MVP 分发。

运行方式（需要 Python 3.11+ 和 cityhash 0.4.10）：

```powershell
python -m pip install --target .verification/static-tools cityhash==0.4.10
python scripts/Extract-Wetype-Mobile.py --apk .verification/wetype-mobile/wetype-android.apk --output .verification/wetype-mobile/reproducible-export --dependency-dir .verification/static-tools
```

解析方法是读取静态哈希表、笔画前缀树、压缩整数与浮点字段。CityHash 用于匹配原数据的哈希键；枚举 Unicode 还原反查键，枚举前缀树还原候选键。没有加载 APK 中的动态库。

重复导出三份 TSV 的字节级 SHA-256 完全相同；未知 APK 哈希会在创建输出目录前被拒绝。结果记录于研究输出目录的 `verification.json`。

## 已确认的数据

| 数据 | 数量 | 含义 |
| --- | ---: | --- |
| 汉字笔画反查记录 | 29,517 | 字符对应一条笔画编码 |
| 笔画前缀 | 34,595 | 前缀对应静态候选列表 |
| 候选记录 | 79,172 | 前缀、存储名次、单字、浮点分数、全码匹配标记 |
| 候选中不同汉字 | 10,579 | 这些字均找到唯一全码候选分数 |
| 未解析的反查键或候选键 | 0 | 全部匹配，不只是抽样 |
| 候选编码/匹配标记矛盾 | 0 | 每条候选均满足反查编码以前缀开头；标记为 1 当且仅当全码相等 |
| 存储候选分数逆序 | 0 | 所有列表按分数降序 |

反查表比可输入候选表更大：**不能据此声称手机笔画模式支持直接输入全部 29,517 个字**。本次解析到的直接候选字符为 10,579 个；最长反查编码为 52 笔。

与现有 Rime 原始字符/码串对照（不做简繁映射）发现：手机反查表只有 70 条码未包含在现有表中，其中 4 条属于上述直接候选字符；另有 5 个手机反查字符未出现在现有表中。多数码在旧表里已经存在，但是否被作为主码、短前缀排序是否合适是另外的问题。完整差异统计见 `docs/mobile-data-comparison.json`。

数字对应：1 横、2 竖、3 撇、4 点/捺、5 折。按本项目键位展示：

| 字 | 手机包编码 | 字母展示 |
| --- | --- | --- |
| 疒 | 41341 | dhpdh |
| 国 | 25112141 | szhhshdh |
| 玉 | 11214 | hhshd |
| 的 | 32511354 | pszhhpzd |
| 天 | 1134 | hhpd |

`D/N` 可以对应同一个数字 4。用户习惯的“国＝szhhsdhh”（25112411）与该手机表主码不同，需要额外容错/个人编码；不能把它当作已经由手机主码表覆盖。

## 权重能做到什么

已导出三份 TSV：

1. `wechat-mobile-strokes.tsv`：29,517 条字符编码。
2. `wechat-mobile-stroke-candidates.tsv`：79,172 条按前缀保存的候选和分数。
3. `wechat-mobile-full-code-scores.tsv`：10,579 个字的全码存储分数，按分数降序。

例如 `41341` 的前十项存储顺序为：病、疫、疗、痛、症、疾、疼、疒、疯、瘦。`3` 的前十项为：的、人、我、个、你、生、会、们、和、年。这些是资源内的顺序，尚未通过手机界面逐项实测。

**存储分数不是原始语料频次。** 同一字在不同长度前缀下的分数不同。例如“国”在 `2` 下为 5.495550，在完整 `25112141` 下为 8.408051。把完整候选分数直接称为“字频”会混入匹配加分。

对现有数据的数值拟合：`分数 ≈ 基础项 + 0.7 × 已输入笔数 / 全码笔数 + 2.3 × 全码匹配`，其中基础项暂取全码分数减 3。79,172 条记录中有 79,167 条在 0.000002 误差内符合，另外 5 条不符合。这是数据推断，**不是已确认的引擎公式，也不作为提取原始字频成功的依据**。

当前结果足以研究、比较手机端的静态候选排序，尚不能声称还原了完整手机体验。上下文调分、个人学习、词组联想、运行时筛选和简繁偏好仍需分别验证。提取腾讯资源不意味着获得其开源或再分发许可；当前保持本地参考用途。

## 对 MVP 的后续决策

### 本地续词资源（2026-10-14 更新）

同一解析脚本现已支持 `sw.bin`：资源版本 1643，SHA-256 为 `095d2c9506c4fcac7b1cee5d498cf7a19cbb24e7718391f9cfe75e3bb3d14ead`。其 4,323 个前字键全部还原，对应 176,329 条长度为 1～3 字的后续串，导出到本地 `wechat-mobile-continuations.tsv`。

每个 payload 包含 1～3 个分组，各组记录尾串长度、Unicode 码点和整数权重。分组数量不能固定写成 3，例如“丁”的记录只有两个分组。脚本验证了全部分组边界、键匹配和组内权重降序；没有未解析键或剩余 payload。

这是一份可重复验证的静态续词资产，不代表手机界面的实时合并顺序，整数权重也未被解释为语料计数。用户已经指定联想界面每次只推荐一个字；1 字分组可作为对应的数据入口，2～3 字分组留作词组研究，不能因此把界面改成整词上屏。

- 主码以手机习惯作为比较基准，特别检查疒、玉及简体字；默认简体、纯笔画、D/N 兼容要求保持。
- 排序先比较“前缀候选列表”，不能只比较全码，也不能简单把一个全局权重覆盖所有情况。
- 未在候选表覆盖的字可以研究开源码表补充，但补充来源与手机来源应可区分。
- 笔顺容错与个人学习独立实现并测试；手机码表的获得不能替代容错算法。
- 在采用新数据/算法前更新已有架构报告，按样例验证，再决定是否部署；本轮没有修改正在使用的输入方案。


## 2026-10-14 词组过滤与本地实现补充

对已校验的Android 4.0.0 libwxhld.so静态分析，StrokesSearcherV2 coroutine位于VA d84a48，StrokeFilter位于d80c08。确认流程为：按首字前缀召回候选→按剩余字数查sw词尾→检查每个字的笔画前缀；native内部星号跳过恰好一笔，内部apostrophe作为分隔。产品的F/7与T/6是本项目键位，不等于native内部字节。

StrokeFilter检查标准码长度至少为该段输入长度，故无需完整笔画即可匹配。部分分数分支含2log10(tail_value+1)、0.5first_value等项，但getter语义与完整最终排序未完全证实。本项目使用独立基线，不宣称获得完整微信算法。

全部176329条词尾可与标准字码关联，missing_codes=0；4234个首字有单字续接98657条，4323个首字有全部词尾。local-only builder已输出整词数据；两引擎实测2分词2、25分词25、251分词251、251分词2?1均可独立召回中国。

为兼容旧librime-lua的整堆回收，生成模块现在以紧凑字符串保存记录、最多缓存64个解码组，保持原始分数和顺序。生成文件哈希已随新manifest更新；原始TSV/APK哈希不变。本机0.4.0部署启用手机词组、逐字联想与个人词库；任意相邻交换容错关闭。

上游Lua translator的回收实现可参考 https://github.com/hchunhui/librime-lua/blob/master/src/lua_gears.cc 。当前上游已采用周期整堆加增量步进，本机旧版的实际耗时与1.17.0差异以独立测试记录为准。
